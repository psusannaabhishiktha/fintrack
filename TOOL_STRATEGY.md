# Tooling strategy

- Tests live in `tests/` and should be run locally. If this is a Python repo, `pytest` is expected.
- Keep CI tasks minimal: run lint, run tests, run security scanning (if applicable).
- Document actual CI commands in this file when known.

---

Feature Usage Log (how Copilot was used in this case study)

1. Inline completion for simple model scaffolding  used to generate initial `models.py` fragments because it speeds repetitive boilerplate.
2. Inline suggestions when writing repository methods  accepted and adapted snippets for SQLAlchemy session usage.
3. Completion for Pydantic validation patterns  used to get validator scaffolding for `split_type` and participant checks.
4. Chat/completion for designing the balance calculation algorithm  used as brainstorming, then implemented and tested manually.
5. Inline code suggestions for FastAPI route signatures  accepted and adjusted headers for auth.
6. Completion for pytest test cases scaffolding  used for initial test structure, then refined to cover edge cases.

Scenario Responses (which Copilot feature I'd use and why)

1) Understanding a complex 500-line function: Use Copilot Chat to ask for a summarised explanation and key responsibilities  chat supports long-form discussion and iterative questioning.
2) Adding consistent error handling across 8 handlers: Use inline completions with a project-level snippet/template (combine with Copilot suggestions) so apply consistent patterns quickly.
3) Verifying a regex handles international phone numbers: Use inline completions plus quick unit tests autogenerated by Copilot; then run tests to confirm edge cases.
4) Enforcing automated code quality checks on every PR: Use Copilot to generate CI config suggestions (e.g., GitHub Actions YAML) and then lock rules in linters; Copilot helps authoring but not enforcement.
5) Reviewing an AI-generated auth module for vulnerabilities: Use Copilot Chat to summarise the module and propose potential security checks, then perform manual code review for cryptographic and auth flaws.
6) Ensuring Copilot follows project conventions: Use a `.github/copilot-instructions.md` and in-editor snippet templates that Copilot will pick up; use explicit prompts with constraints.

Limitations Encountered (real examples from this case study)

1. Missing authorization: Prompt: "Generate Transaction model/service..." produced functions that expose data without auth. Detection: manual code review. Fix: Added header-based auth check and service-level enforcement.
2. Unsafe destructive operation: Copilot created `delete_all_transactions`. Detection: manual review and risk analysis. Fix: removed from public API and documented as admin-only operation.
3. Bad DB choice for concurrency: Copilot used raw SQLite with no pooling. Detection: reasoning about concurrency and production needs. Fix: migrated to SQLAlchemy and configurable DB URL.

These limitations show Copilot is a powerful productivity tool but requires human oversight for security, authorization, and operational correctness.
